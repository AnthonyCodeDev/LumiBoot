# v64: 64-bit browser engine

LumiBoot integrates `speedyHKjournalist/v64` as the lazy `V64Provider`. The
runtime is pinned to commit
`74d2bafcc7d568e2ab4374804e176f1a8a350f61` (27 October 2026); every published
WASM, Worker, plugin, BIOS and WebGPU asset is locked by byte size and SHA-256
in `scripts/v64-assets.lock.json`.

The core binaries (`v86*.wasm`, `libv86.mjs`, the two workers) are that
revision **with** [`scripts/patches/v64-ioapic-irq0-gsi2.patch`](../scripts/patches/v64-ioapic-irq0-gsi2.patch)
applied: ISA IRQ 0 -> I/O APIC input 2 (with the matching MADT interrupt source
override), HPET main-counter period 100 ns, and the extended CPUID leaves the
Windows 11 HAL requires. The lock file records it as `patch`, `patchFile` and
`build.patches`, so an unpatched rebuild cannot be installed silently.

There is no virtualization backend. CPU emulation, devices, disk I/O and
rendering execute in the visitor's browser.

## Implemented and verified here

- x86-64 CPU with the v64 WebAssembly page-tier JIT.
- A dedicated CPU Worker.
- 1–8 guest cores; `parallel: "auto"` uses one Worker per vCPU when the page is
  cross-origin isolated, with v64's cooperative fallback otherwise.
- ISO, kernel/initramfs and RAW hard-disk boot paths.
- Persistent RAW disks in OPFS. LumiBoot copies imported bytes once to
  `opfs:lumiboot/v64/disks/<system>.img`; `disk_option: "read_write"` writes the
  guest's changes back from the CPU Worker.
- VirtIO, NE2000 and E1000 network devices through the existing LumiBoot
  network profiles; offline remains the default.
- PS/2 keyboard/mouse, plus an opt-in USB host controller with a HID tablet and
  a HID boot keyboard (`v64UsbKeyboard`, see below), VGA, optional Intel HD
  Audio, i440FX/Q35 and ACPI.
- Bochs VGA by default; VMware SVGA II and virtio-gpu plugins plus the v64
  WebGPU renderer are available when a profile selects them and WebGPU exists.
  The adapter is a profile `extra` option (`v64Graphics`), which `V64Provider`
  now reads from the profile when the application passes no override: before
  that, the catalogue value was silently ignored and every v64 profile ran
  `bochs_vga`.
- Real E2E boot of the unmodified official Alpine 3.24.0 x86_64 `virt` ISO. The
  test waits for the guest's `localhost login:` prompt, logs in, and proves
  `uname -m` is `x86_64`. A successful run took about 1.5 minutes on two cores.

## Two-media boot (ESP + system disk)

A local disk manifest may declare a second, optional file:

```json
{ "esp": { "fileName": "esp.img", "url": "/images/<ref>/esp.img", "size": 67108864 } }
```

The field is additive. `disk` and `boot` keep describing the installed system
disk, so `boot.url === disk.url` and `boot.size === disk.size` stay true with or
without an ESP, and a manifest that declares none behaves exactly as before.
`V64Provider` changes the drive layout only when `esp` is present: the ESP is
mounted as `hda` (SATA port 0) and the system disk as `hdb`, both with
`async: true` so they are read lazily over HTTP Range. Sizes come from the
manifest; an ESP is typically 64 MiB. The order is an invariant rather than a
preference: the NVRAM image served as `firmware.vars` carries a `Boot0001` entry
that points at SATA port 0, so swapping the two drives would leave the guest
with no bootable device. v86 ignores the field, having no UEFI firmware.

`fileName` is optional, purely local, and never validated against a machine
path: it is the *served* name (exactly like `disk.fileName`), it must be a plain
name, and the schema requires it to be the last segment of `esp.url`. Without
it the manifest is still valid, but the dev middleware cannot locate the file
next to the manifest and therefore does not serve the ESP at all (a manifest
with `{ "url", "size" }` only is what a published, non-local image would
declare). The dev middleware also refuses any `fileName` that escapes
`images/<ref>/`, drops the `esp` block from the served manifest when the file is
missing or its size disagrees, and answers a plain `404` on that route. The
system disk keeps being served in every one of those cases.

### Producing a two-media manifest

`--esp` is part of the shared generator, so every `prepare-*-asset.mjs` wrapper
accepts it. It requires `--engine v64` (v86 has no UEFI firmware), copies the
file next to the manifest under its own name, hashes it in full and records
`{ fileName, url, size }`; the SHA-256 goes to the log and `provenance.txt`
(the ESP block itself carries no checksum). Nothing else changes: without
`--esp`, the generated manifest is byte-identical to the previous one.

```text
pnpm assets:windows11:prepare -- --source "<path>\Windows11-x64.img" --esp "<path>\esp.img"
pnpm assets:windows11:check
```

or, with the shared generator directly:

```text
node scripts/prepare-windows7-asset.mjs --engine v64 --architecture x86_64 \
  --source images/windows-11-x64/disk.img \
  --firmware-vars images/windows-11-x64/uefi-vars.fd \
  --esp images/windows-11-x64/esp.img
```

The result is `images/<ref>/{disk.img,esp.img,uefi-vars.fd,manifest.json}`; the
dev middleware logs `ESP ready (HTTP Range): /images/<ref>/esp.img` and V64Provider
mounts it on `hda`. `--check` verifies the recorded ESP size, looking for the
file next to the manifest and then next to the disk.

### NVRAM: is a `Boot0001` entry required?

Not always. OVMF ships a boot manager that, when the NVRAM holds no usable boot
option, falls back to the UEFI removable-media path `\EFI\BOOT\BOOTX64.EFI` of
every attached block device; the standalone harness that booted OpenCore from an
ESP had been started with a fresh copy of `edk2-x86_64-vars.fd` and no boot
entry, and it reached the picker. So an ESP that carries
`\EFI\BOOT\BOOTX64.EFI` — the layout OpenCore, GRUB and most Linux installers
write — boots from a virgin template, which is also what `V64Provider` uses when
the manifest declares no `firmware.vars` (`/v64/ovmf-vars.fd`, the upstream
blank store).

A `Boot0001` entry is required in two cases:

- the ESP only carries the vendor path, e.g. `\EFI\Microsoft\Boot\bootmgfw.efi`
  (a stock Windows layout has **both**, so it also boots from the fallback). With
  a blank NVRAM and no `\EFI\BOOT\BOOTX64.EFI`, OVMF drops to its built-in shell;
- the profile asks for `secure_boot`, since only a boot option can be validated.

The entry has to be *inside the served file*: `firmware.vars` is fetched once per
start and is never written back, so an entry OVMF creates during a session is
lost on reload. The documented way to produce such a store is to let OVMF create
it:

1. seed the store from QEMU's template
   (`Copy-Item "%ProgramFiles%\qemu\share\edk2-i386-vars.fd" images\<ref>\uefi-vars.fd`,
   the template matching `edk2-x86_64-code.fd` — the name carries the toolchain
   family, not the guest bitness); `images/windows-11-x64/README.md` holds the
   full reference procedure;
2. boot that store with QEMU, the ESP on **AHCI port 0** and the system disk on
   port 1 (`-drive if=pflash,format=raw,readonly=on,file=...code.fd
   -drive if=pflash,format=raw,file=...vars.fd -device ich9-ahci,id=sata
   -device ide-hd,drive=esp,bus=sata.0 -device ide-hd,drive=disk,bus=sata.1`),
   select the ESP's `bootmgfw.efi` once in the firmware menu;
3. shut the guest down cleanly, stop QEMU, and serve that file as
   `firmware.vars`. OVMF rewrites `BootOrder`/`Boot0001` with the new device path,
   and the port-0 ordering is exactly what `V64Provider` reproduces.

## Guest input: USB HID keyboard

A profile can put the page's keys on a **USB HID boot keyboard** instead of (and
alongside) the PS/2 one. The engine option is opt-in, so a profile without it
gets exactly the configuration it had before — no USB controller, no plugin:

```json
{ "extra": { "v64UsbTablet": true, "v64UsbKeyboard": true, "v64UsbController": "uhci" } }
```

The three flags are read from the launch profile's `configuration.extra` and may
be overridden per start through `VMConfiguration.extra`; the catalogue's `extra`
bag only carries scalars, hence one flag per device (like `v64Hpet`).
`V64Provider` turns them into
`usb: { controller, tablet, keyboard, plugin_path: "/v64/v86-usb.js" }`;
`controller` defaults to `uhci`, and a request that names neither device emits
no `usb` key at all. `tablet` is the absolute pointer libv86 already drives
(`mouse-absolute`/`mouse-click`); `keyboard` is `v86-usb.js`'s HID keyboard,
which the plugin attaches after the tablet's port.

Typing goes through the bus, one transition per report:

```js
emulator.bus.send('keyboard-usage', [0x04, true]); // 'a' down
emulator.bus.send('keyboard-usage', [0x04, false]); // 'a' up
```

`V64Provider` attaches `usb-keyboard-adapter.ts`, which listens on `window`
(as libv86's own PS/2 keyboard does) and translates `KeyboardEvent.code` — then
`KeyboardEvent.key` when a `code` is missing — into HID usages: `0x04`–`0x1D`
`a`–`z`, `0x1E`–`0x27` `1`–`0`, `0x28` Return, `0x29` Escape, `0x2A` Backspace,
`0x2B` Tab, `0x2C` Space, `0x2D`–`0x38` the US punctuation keys, `0x4C` Delete,
`0x4F`–`0x52` the arrows, and the modifiers `0xE0`–`0xE7` (left/right Control,
Shift, Alt, GUI). Modifiers are held as their own transitions, so `Shift`+`A`
sends `0xE1` down, `0x04` down/up, `0xE1` up; both sides are tracked
separately, auto-repeat is coalesced, a `<input>`/`<textarea>`/`<select>` keeps
its own keys (the serial console is a textarea), and a `blur` releases
everything held so no modifier sticks. An unmapped key is dropped, never thrown.

Limits: the mapping is **US** only — a non-US layout sends the usage of the
physical key, which is what the guest's own US layout expects; shifted symbols
are the guest's business (Shift is a separate transition, there is no implicit
Shift); there is no guest-side typematic repeat (the page's auto-repeat is
coalesced into one transition), so a held key types once; and holding a key for
the guest's own repeat requires the guest's keyboard driver, which is outside
LumiBoot's control.

## Emulated SMC (`APP0001`)

macOS never boots past `Waiting for DSMOS...` without the Apple SMC: lion's
`Dont_Steal_Mac_OS_X` reads the 64-character OSK key from it and only publishes
the `DSMOS` service when the key matches the one it carries. LumiBoot's engine
now has that chip, `smc: true`, modelled on QEMU's `isa-applesmc`
(`src/smc.js`):

```json
{ "machine_type": "q35", "acpi": true, "smc": true, "net_device": { "type": "none" } }
```

The option is off by default (`platform.smc`) and only `q35` accepts it; on
`i440FX` the floppy controller keeps IRQ 6, so `create_platform` refuses the
combination. A launch profile asks for it with a single `extra` flag, like the
USB devices and the HPET:

```json
{ "extra": { "v64Smc": true, "v64Machine": "q35", "v64Firmware": "uefi" } }
```

`v64Smc` is read from the launch profile's `configuration.extra` and may be
overridden per start through `VMConfiguration.extra`. When it is `true`,
`V64Provider` emits `smc: true` and enforces the two constraints below itself,
before the engine starts, so a bad profile gets a readable `START_FAILED`
instead of a libv86 `create_platform` throw:

- **q35 only**: `v64Machine` (or `hardwareProfile.machine`) may not say
  `i440fx` — the message names `machine_type "q35"`; an absent `v64Machine` is
  promoted to `q35`, since i440FX cannot carry the device at all.
- **No NE2000**: an explicit `hardwareProfile.network: "ne2k"` is refused (the
  message names the shared `0x300-0x31F` ports); otherwise the provider
  **forces** `net_device: { type: "none" }`, because an SMC profile is offline
  by design. `virtio`/`e1000`/`none` therefore all end up with no guest NIC,
  and the network relay is simply never used.

Without the flag no `smc` key is emitted and the engine configuration is
unchanged (Windows 11, Alpine, Fedora keep their existing layout). A complete
macOS `extra` bag is `v64Smc: true`, `v64Machine: "q35"`, `v64Firmware: "uefi"`,
`v64UsbTablet: true`, `v64UsbKeyboard: true` (plus `v64UsbController: "uhci"`
when the default is not wanted). That bag is exactly the published `macos-lion-x64`
profile (see the compatibility table below), with `v64CpuCores: 1` and
`hardwareProfile.network: "none"`.

- Ports: data `0x300`, command/status `0x304`, error `0x31E`, all 8-bit (a
  16- or 32-bit access is split into byte accesses, as QEMU's region does).
- Commands: `0x10` READ (the only one implemented, as in QEMU 8.2), `0x11`
  WRITE, `0x12` GET_KEY_BY_INDEX and `0x13` GET_KEY_TYPE answer status `0x08`
  with error `0x82`; macOS then falls back to READ of each key ("old SMC mode").
- Status: `0x00` done, `0x01` data ready, `0x02` busy, `0x04` acknowledge,
  `0x08` new command. Errors (`0x1E`): `0x84` key does not exist, `0x82` bad
  command, `0x81` data written for a bad command, `0x80` interrupted command.
- Keys: `REV ` = `01 13 0F 00 00 03`, `OSK0`/`OSK1` = 32 bytes each (QEMU's
  `-osk` default, `ourhardworkbythesewordsguardedpleasedontsteal(c)AppleComputerInc`),
  `NATJ`, `MSSP` and `MSSD` = one byte each.
- ACPI: `Device(SMC)` with `_HID = APP0001`, `_CRS = IO(0x300, length 0x20)`
  and **IRQ 6**, only when `platform.smc` is set. `AppleSMC.kext` matches that
  device, registers the interrupt source and fails to start
  (`failed to create fInterruptSource`) when another device already owns IRQ 6:
  so on `q35` the `FDC0` device gives IRQ 6 up (QEMU's `q35` has no floppy
  controller at all, `no_floppy = 1`; the ports and the DMA channel stay).
- I/O `0x300` belongs to the **NE2000** as well: `net_device` type `ne2k` — the
  default — puts that ISA card's data port at `0x300`
  (`src/net_adapters/ne2k/ne2k.js`), so it would mask the SMC. There is no way
  to move either device, so the combination is refused instead of silently
  letting one win:

  ```text
  smc: true and the NE2000 (net_device type "ne2k", the default) both use the I/O ports 0x300-0x31F: the NE2000's data port is 0x300, the Apple SMC's too. Give net_device: { type: "none" } (or "e1000", which is on MMIO) with smc, or leave smc off
  ```

- Snapshots: the SMC is slot 112 of the CPU state (`src/cpu.js`, after the USB,
  TPM and pflash slots), and `validate_state` accepts a snapshot into a machine
  with the same choice only — the ACPI namespace differs, so a snapshot taken
  without `APP0001` is refused instead of restored into a machine that has it.
- Build: the patch adds `src/smc.js` to `CORE_FILES` in the `Makefile`, so the
  device is in `libv86.mjs` **and** `cpu-worker.js` (and `vcpu-worker.js`); the
  WASM core is untouched.

Proof, outside LumiBoot (the harness lives in the git-ignored
`apps/web/public/v64/`, the ESP carries no Apple kext, `net_device` is `none`,
production bundles as installed by `scripts/build-v64-assets.sh`):

```text
wsl -d Ubuntu -e bash scripts/build-v64-assets.sh   # the seven files, verified
node %TEMP%\opencode\macos-lion\smc\serve-v64-smc.mjs 5200
node %TEMP%\opencode\macos-lion\smc\run-smc-prod.mjs --out apps\web\public\v64\smc-prod \
  --minutes 16 --capture 60 \
  --query "esp=esp-smc-noadd.img&hdb=lion-autologin.img&hdbsize=8589934592&disks=/v64/wb1&wbmode=ro&worker=1&cores=1"
```

The harness page (`apps/web/public/v64/macos-harness-smc.html`), the static
server and the Playwright driver are campaign tools, not published. The run's
screenshots, `meta.json`, serial log and report are in
`apps/web/public/v64/smc-prod/` (git-ignored): `cap_0184s_tick.png` carries
`DSMOS has arrived`, `cap_0304s_tick.png` the open desktop.

`DSMOS has arrived` appears on the guest's verbose console with an **empty**
`Kernel > Add` (no `AppleSMC.kext`/`DontSteal.kext` on the ESP), and the kexts
are loaded by `kextd` from `/S/L/E` because `APP0001` exists. Measured with the
production bundles and the CPU Worker: the kernel reaches `Waiting for
DSMOS...` at 160 s and `DSMOS has arrived` at 184 s, the Lion desktop (open
autologin session) at 304 s; the disk's own FakeSMC 5.3.901 stands down
(`FakeSMC: [Fatal] SMC device detected, will not create another one`), so the
`APP0001` device is the only SMC AppleSMC.kext talks to. The prototype, which
ran the devices on the page's thread, took about 700 s for the same point.
A host-side trace of the device (`SMC|key|OSK0|len=32`) came from that
prototype build, which traced every key; the production device logs nothing.

Alongside it, `scripts/patches/v64-ata-power-management.patch` completes ATA STANDBY `0xE2`, IDLE `0xE3` and SLEEP `0xE6` with DRDY + IRQ, which removes the AHCI livelock (`0xE6` used to leave `tfd=0x50`); `v86-usb.js` is now pinned in `scripts/v64-assets.lock.json` and `node scripts/prepare-v64-assets.mjs --check` passes 19/19. Measured limits: **US key mapping only** (no AZERTY), the menu bar is painted **late** (300-460 s), **2 starts in 5 froze on a grey screen** (instruction counter stalled ~275 s, after an abrupt engine stop; not USB-related, the proof was redone on a fresh copy), and the installed volume is a local, non-distributable artifact. The **ESP constraint is gone for the product ESP**: because the engine emulates the Apple SMC, the published `esp.img` injects **no kext** — OpenCore files only, no Apple binary — while the operator's older three-kext `esp-fsmc9.img` (`AppleSMC.kext`, `DontSteal.kext`, FakeSMC) stays unpublishable. **Booted inside LumiBoot on 2026-11-11**: the `macos-lion-x64` profile, image and manifest exist and the product reaches the Finder desktop in **245.0 s** with no kext injected, recorded by `tests/e2e/macos-lion-desktop.spec.ts` - [`images/macos-lion-x64/README.md`](../images/macos-lion-x64/README.md) |

Windows media and macOS media are never distributed by LumiBoot. No Windows 8.1
entry exists on the v64 engine: the catalogue's Windows 8.1 system is the x86
profile (`windows-8-1-x86`) running on v86 from the operator's local RAW disk,
declared `validated: true` but outside the v64 compatibility table.

## Building the vendored engine

`scripts/build-v64-assets.sh` reproduces the seven locked engine files from
source; it never commits and only writes the git-ignored
`apps/web/public/v64/`.

- Revision: `74d2bafcc7d568e2ab4374804e176f1a8a350f61`, cloned with
  `core.autocrlf=false`. This is mandatory: a CRLF checkout makes the
  executable build scripts fail with `node\r: Permission denied`.
- Patches, applied in `build.patches` order:
  1. `scripts/patches/v64-ioapic-irq0-gsi2.patch` (IRQ0 -> GSI2, HPET 100 ns,
     extended CPUID leaves);
  2. `scripts/patches/v64-ata-power-management.patch` (ATA STANDBY `0xE2`,
     IDLE `0xE3`, SLEEP `0xE6` complete with DRDY like STANDBY/IDLE IMMEDIATE,
     so the AHCI port no longer latches `halted` on the macOS driver's
     power-management commands);
  3. `scripts/patches/v64-usb-keyboard.patch` (a USB HID boot keyboard in the
     USB plugin, `src/usb/hid_keyboard.js`, opt-in `usb.keyboard`, typed into
     with the bus's `keyboard-usage` and announcing `usb-keyboard-active`:
     macOS Lion ships no PS/2 driver);
  4. `scripts/patches/v64-smc-device.patch` (the Apple SMC of QEMU's
     `isa-applesmc`, `src/smc.js`, opt-in `smc: true` on `q35`: READ on
     `0x300`/`0x304`/`0x31E`, the `REV `/`OSK0`/`OSK1`/`NATJ`/`MSSP`/`MSSD`
     keys, `Device(SMC)` `_HID "APP0001"` with I/O `0x300-0x31F` and IRQ 6 in
     the ACPI tables, the `q35` `FDC0` giving IRQ 6 up, the NE2000 conflict
     refused, and the snapshot slot; see "Emulated SMC (`APP0001`)").
- Targets: `make build/v86.wasm build/v86-fallback.wasm
  build/v86-parallel.wasm build/libv86.mjs build/cpu-worker.js
  build/vcpu-worker.js build/v86-usb.js`, one job by default (`JOBS=<n>` to
  override).
- Verification: sizes and SHA-256 of the seven outputs are compared with
  `scripts/v64-assets.lock.json` before and after installation. A mismatch
  aborts the script; the lock is never adjusted to hide a non-reproducible
  build.

```text
wsl -d Ubuntu -e bash scripts/build-v64-assets.sh
V64_BUILD_DIR=/tmp/v64 SKIP_INSTALL=1 bash scripts/build-v64-assets.sh
node scripts/prepare-v64-assets.mjs --check
```

The scratch clone lives in `$V64_BUILD_DIR` (default
`${TMPDIR:-/tmp}/lumiboot-v64-build`) and is hard-reset and cleaned on every
run, so the build is idempotent. The Linux environment needs `git`, `make`,
`node`, `java` (the closure compiler jar ships in the repository) and `cargo`
with the `wasm32-unknown-unknown` target.

## Hosting requirements

Parallel cores require these headers, enabled by default in the Vite dev and
preview servers:

```text
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: same-origin
```

Production hosting must send equivalent headers. Cross-origin disks must also
be CORS/CORP-compatible. Set `LUMIBOOT_COOP_COEP=0` only when the host cannot
provide isolation; v64 then keeps multiple guest cores but schedules them
cooperatively on one host thread.

# v64: 64-bit browser engine

LumiBoot integrates `speedyHKjournalist/v64` as the lazy `V64Provider`. The
runtime is pinned to commit
`74d2bafcc7d568e2ab4374804e176f1a8a350f61` (27 October 2026); every published
WASM, Worker, plugin, BIOS and WebGPU asset is locked by byte size and SHA-256
in `scripts/v64-assets.lock.json`.

The core binaries (`v86*.wasm`, `libv86.mjs`, the two workers) are that
revision **with** [`scripts/patches/v64-ioapic-irq0-gsi2.patch`](../scripts/patches/v64-ioapic-irq0-gsi2.patch)
applied: ISA IRQ 0 -> I/O APIC input 2 (with the matching MADT interrupt source
override), HPET main-counter period 100 ns, and the extended CPUID leaves the
Windows 11 HAL requires. The lock file records it as `patch`, `patchFile` and
`build.patches`, so an unpatched rebuild cannot be installed silently.

There is no virtualization backend. CPU emulation, devices, disk I/O and
rendering execute in the visitor's browser.

## Implemented and verified here

- x86-64 CPU with the v64 WebAssembly page-tier JIT.
- A dedicated CPU Worker.
- 1–8 guest cores; `parallel: "auto"` uses one Worker per vCPU when the page is
  cross-origin isolated, with v64's cooperative fallback otherwise.
- ISO, kernel/initramfs and RAW hard-disk boot paths.
- Persistent RAW disks in OPFS. LumiBoot copies imported bytes once to
  `opfs:lumiboot/v64/disks/<system>.img`; `disk_option: "read_write"` writes the
  guest's changes back from the CPU Worker.
- VirtIO, NE2000 and E1000 network devices through the existing LumiBoot
  network profiles; offline remains the default.
- PS/2 keyboard/mouse, VGA, optional Intel HD Audio, i440FX/Q35 and ACPI.
- Bochs VGA by default; VMware SVGA II and virtio-gpu plugins plus the v64
  WebGPU renderer are available when a profile selects them and WebGPU exists.
  The adapter is a profile `extra` option (`v64Graphics`), which `V64Provider`
  now reads from the profile when the application passes no override: before
  that, the catalogue value was silently ignored and every v64 profile ran
  `bochs_vga`.
- Real E2E boot of the unmodified official Alpine 3.24.0 x86_64 `virt` ISO. The
  test waits for the guest's `localhost login:` prompt, logs in, and proves
  `uname -m` is `x86_64`. A successful run took about 1.5 minutes on two cores.

Prepare and verify:

```text
pnpm assets:v64:prepare
pnpm assets:v64:alpine
sudo ./images/alpine-3-24-x86-64/build.sh
pnpm assets:v64:alpine:xfce
pnpm assets:v64:check
VM_E2E_ASSETS=1 pnpm exec playwright test tests/e2e/session-alpine-v64.spec.ts --project=chromium --workers=1
```

The E2E server is Playwright's port 5200. Do not run this test against the
developer's port 5173.

## Compatibility status

| Guest | LumiBoot status | Evidence / limit |
| --- | --- | --- |
| Fedora 44 x86-64 | verified | Real boot and `x86_64` userspace command in `session-fedora.spec.ts`; live ISO built by `images/fedora-44-x86-64/build.sh`, booted from its own GRUB El-Torito record (`boot.cdromOnly`), because the injected-bzimage path hard-codes the initrd at 64 MiB and a kernel that decompresses above it overwrites it |
| Alpine 3.24 x86-64 | verified | Real boot and `x86_64` userspace command in `session-alpine-v64.spec.ts` |
| Graphical Linux x86-64 | verified | Real XFCE desktop, `fedora-44-x86-64-xfce`: `tests/e2e/desktop-fedora-xfce.spec.ts` waits for the guest's `LUMIBOOT_DESKTOP_READY` marker, then polls the VGA canvas until it is painted and requires three stable measurements (mean luminance 172/255, 99.8 % non-black at 1024x768). Adapter measured on the same ISO: `bochs_vga` (kept) and `virtio_gpu` both draw the desktop; `vmware_svga` never presents on the canvas without WebGPU (`vmwgfx` takes the session to the VMware SVGA device, which v64 can only present through its WebGPU renderer, and headless Chromium logs `No available adapters.`) |
| Alpine 3.24 x86-64 XFCE | verified | Real XFCE desktop, `alpine-3-24-x86-64-xfce`: `tests/e2e/desktop-alpine-xfce.spec.ts` boots the published image (305 135 616 B ISO, preinstalled squashfs rootfs) and waits for the guest's `LUMIBOOT_DESKTOP_READY` marker, printed 132.7 s after the start click, then polls the VGA canvas and requires three stable measurements at 1024x768 (mean luminance 58.8/255, 99.6 % non-black, 217 colours). The rootfs is mounted read-only with an overlayfs RAM upper layer by a custom initramfs `init`, because the stock `virt` ISO installs its rootfs with `apk add` at every boot and cannot carry XFCE |
| Windows 7 x64 | not verified | Upstream lists Windows 7 as unverified |
| Windows 10 x64 | not verified | Upstream lists Windows 10 as unverified |
| Windows 11 x64 | verified (boot to sign-in) | Local UEFI/GPT RAW disk booted through OVMF (`edk2-stable202408`) by `V64Provider` on `machine_type: q35` + ICH9 AHCI, with `cpu_features: x86-64-v2`, `e1000` and the operator's OVMF variable store served next to the disk (`firmware.vars`). Real boot proven with the patched build (`scripts/patches/v64-ioapic-irq0-gsi2.patch`, recorded as `patch`/`patchFile` in `scripts/v64-assets.lock.json`): ISA IRQ 0 now reaches I/O APIC input 2 (plus the matching MADT interrupt source override), the HPET main-counter period is 100 ns and the extended CPUID leaves (`0x80000001`, `0x80000007`, `0x80000008`) are served. The former `0x5C` `HAL_INITIALIZATION_FAILED` bugcheck is gone (`KiBugCheckData = 0`); the guest reaches the Windows 11 sign-in screen (~1138.6 MiB read in the 720 s probe) and `tests/e2e/windows11-desktop.spec.ts` reached a stable 1280x800 VGA screen in 1932.4 s (1 577.47 MiB over 44 586 Range requests). The desktop login is still under validation; no TPM 2.0 and no Secure Boot, so BitLocker must stay disabled |
| ARM64 Linux | upstream-capable, not exposed by `V64Provider` yet | Needs the separate ARM64 WASM core, QEMU `virt` machine, direct kernel/initrd/device-tree boot and a dedicated manifest contract |
| macOS | unsupported | No validated v64 guest, no Apple hardware model, and licensing restricts use to Apple-branded hardware. LumiBoot makes no compatibility claim |

Windows media and macOS media are never distributed by LumiBoot. No Windows 8.1
entry exists on the v64 engine: the catalogue's Windows 8.1 system is the x86
profile (`windows-8-1-x86`) running on v86 from the operator's local RAW disk,
declared `validated: true` but outside the v64 compatibility table.

## Hosting requirements

Parallel cores require these headers, enabled by default in the Vite dev and
preview servers:

```text
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: same-origin
```

Production hosting must send equivalent headers. Cross-origin disks must also
be CORS/CORP-compatible. Set `LUMIBOOT_COOP_COEP=0` only when the host cannot
provide isolation; v64 then keeps multiple guest cores but schedules them
cooperatively on one host thread.

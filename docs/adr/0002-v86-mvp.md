# ADR 0002 — v86 comme premier moteur (MVP Debian)

- **Statut :** accepté
- **Date :** 2026-10-14

## Contexte

Plusieurs moteurs x86 en navigateur existent (v86, CheerpX, JSLinux…). Le premier système
opérationnel doit être un Debian réel, testable et reproductible.

## Décision

- Retenir **v86** (licence BSD-2-Clause) pour la première version locale : il émule un véritable PC,
  son intégration est contrôlable et le code est ouvert.
- Cible de démarrage : **Debian 12 Bookworm i386**, pas Debian 13 (Trixie a supprimé le noyau et
  l'installateur i386 natifs).
- Le moteur est chargé **paresseusement** (`@lumiboot/provider-v86`), uniquement lorsqu'une session
  le requiert, derrière `VMProvider`.

## Alternatives écartées

- **CheerpX** : runtime propriétaire, auto-hébergement soumis à conditions de licence ; conservé
  comme moteur alternatif possible, non retenu pour le MVP.
- **v86 pour Windows 10/11 x64 ou macOS** : impossible (pas de x86-64, pas de multicœur, pas de
  virtualisation matérielle de l'hôte).

## Conséquences

- Le provider v86 est intégré et enregistré dans le registre ; il charge v86 (WASM) paresseusement
  au lancement d'une session, jamais au chargement de l'application.
- Debian reste au statut `planned` tant que l'image réelle n'est pas construite, publiée et validée
  par le smoke test dans le navigateur ; `engines.v86.integrated` ne passe à `true` qu'à ce moment.
  `booting → running` se fait au plus tôt sur le marqueur `LUMIBOOT_GUEST_READY` émis par l'invité
  sur `ttyS0` (chemin rapide) ; si le marqueur n'arrive pas dans le délai imparti, le dépassement
  vaut désormais `running` (repli : l'émulateur tourne et l'écran est visible) — ce n'est plus une erreur.
- Aucune image binaire n'est committée : seul un manifeste (URL, taille, sha256, licence) circule,
  validé par un schéma Zod strict (`@lumiboot/vm-assets`).
